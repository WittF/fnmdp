# B站会员购 `getV2` 接口：实时票务状态监控接入指南

> 适用对象：基于本接口构建「演出/漫展实时票务状态监控大盘」的开发者。
> 数据来源：对若干公开项目的实测 + 官方工程博客《B站票务抢购下单流程演进》+ 边缘响应头分析。
> 最后更新：2026-06-20。

---

## 1. 这个接口是什么

```
GET https://show.bilibili.com/api/ticket/project/getV2
    ?id=<项目ID>&project_id=<项目ID>&requestSource=neul-next
```

它是会员购**项目商详只读接口**：输入一个项目 ID，返回该项目的全部展示信息——场次、票种(SKU)、价格、售卖状态、开售时间、场馆、退票规则、热度等。

- **只读**：不下单、不需要登录态（未登录也能读，返回 `mid:0`）。
- **公开**：不需要 WBI 签名、不需要 cookie 鉴权。
- **它是低频兜底/交叉校验源**：真正的库存/下单在 `order/prepare`、`order/createV2`，但那些需要登录态且是写接口，**不适合做监控**。本项目主轮询走 `mall items_detail/info`，字段语义与本页描述的 getV2 商详基本一致；getV2 因 412 风控只保留低频用途。

---

## 2. 对实时监控系统的价值（能监控什么）

`getV2` 提供了构建票务状态大盘所需的几乎全部信号。按层级整理如下。

### 2.1 项目级状态信号

| 字段 | 类型 | 监控用途 |
|---|---|---|
| `sale_flag` / `sale_flag_number` | 文案 / 码 | **核心售卖状态**：`1`=未开售、`2`=在售/预售、`4`=已售罄。大盘主状态灯。 |
| `status` / `is_sale` | int | 项目是否上架可售（`1`/`1`=正常）。 |
| `sale_begin` / `sale_start` / `sale_end` | 时间戳(秒) | 开/停售窗口，用于「距开售倒计时」「售卖中/已结束」判定。 |
| `count_down` / `bs_countDown` | 秒 | 服务端给出的开售倒计时，**直接用它而非本地算**（见 §5.3）。 |
| `current_time` | 时间戳(秒) | **服务端当前时间**，用于和本地时钟对齐、修正倒计时漂移。 |
| `price_low` / `price_high` | int（**分**） | 价格区间，`/100` 得元。绘制价格带。 |
| `salable_price_low/high` | int（分） | **当前可售**价格区间（区别于全部票价区间）。 |
| `wish_info.count` | int | 心愿单/想去人数 → **热度指标**，可做趋势曲线。 |
| `hotProject` | bool | 是否热门项目（影响风控强度，见 §4）。 |

### 2.2 场次级（`screen_list[]`）

| 字段 | 用途 |
|---|---|
| `id` | 场次 ID（监控的稳定主键之一）。 |
| `name` / `start_time` | 场次名/演出时间，做多场次分行展示。 |
| `saleFlag.display_name` | **该场次**售卖状态（项目可能整体在售但某场已售罄）。 |
| `clickable` | 该场次是否可购（`false` = 不可点：未开售或售罄）。 |
| `sale_start` / `sale_end` | 该场次独立的售卖窗口。 |

### 2.3 票种级（`screen_list[].ticket_list[]`）——监控的最小粒度

| 字段 | 用途 |
|---|---|
| `id` (= `sku_id`) | **SKU 稳定主键**，按它做时间序列。 |
| `desc` | 票种名（如「大会员提前抢-S级」「VIP票(含礼包)」）。 |
| `price` | 单价（分）。 |
| `sale_flag.display_name` / `sale_flag.number` | **单 SKU 售卖状态**（`未开售`/`已售罄`/在售）。判断"某档票有无"的主状态字段。 |
| `clickable` | 该 SKU 当前是否可下单。 |
| `sale_start`（字符串）/ `saleStart`（时间戳） | 该 SKU 的开抢时间。不同档位可能分批开售。 |
| `num` | **可购买数量 = `min(真实库存, 限购上限)`**，是**告急/精确余量**信号。见 §5.1。 |
| `static_limit.num` | **限购上限**（每单/每证可买上限），恒定，与余票无关。`num` 的封顶值。 |
| `num_type` | `num` 当前受何约束（`2`≈被限购盖住=库存足，`1`≈露出真实库存）。辅助信号，以 `num` vs `static_limit.num` 比较为准。 |
| `less_vt` / `less_lv` | 购买门槛（`less_vt:1`=需大会员）。 |

### 2.4 典型监控场景

1. **开售提醒**：轮询 `sale_flag_number` 由 `1`→`2`，或 `clickable` 由 `false`→`true` 时推送。
2. **回流捡漏**：售罄(`已售罄`)的 SKU 偶尔因他人弃单回流，监控 `sale_flag.display_name` 由「已售罄」→「在售」即触发告警。**这是漫展监控最高价值的场景。**
3. **价格/档位变动**：`ticket_list` 增减、`price` 变化、新增白名单档位。
4. **热度趋势**：`wish_info.count` 随时间的曲线。
5. **多项目状态墙**：N 个项目 × M 场次 × K 票种的状态矩阵。

## 3. 推荐的监控架构

```
	┌──────────────┐   高频主轮询   ┌──────────────┐   diff   ┌──────────┐   推送   ┌────────┐
	│ 采集器(单出口)│ ───────────▶ │ mall 商详接口 │ ───────▶ │ 状态比对  │ ──────▶ │ 大盘/告警│
	│ 串行+退避     │   ~1 req/s    │              │  仅存变更 │ (按SKU)   │         │        │
	└──────┬───────┘               └──────────────┘          └──────────┘         └────────┘
	       │
	       └──────── 低频兜底/交叉校验 ───────▶ getV2 接口
```

要点：
- **采集与展示分离**：采集器把每次 `getV2` 结果归一化为 `(project, screen, sku) → {sale_flag, clickable, price, ts}`，只持久化**变更**（diff），前端大盘订阅变更流。
- **单一采集出口**：所有项目共用一个低频采集器，**不要每个项目/每个用户各开一个轮询**（会叠加到同一出口 IP 上触发风控，见 §4）。
- **售卖状态以 `sale_flag`/`clickable` 为准；余量用 `num` vs `static_limit.num`**（§5.1）。
- **getV2 必须低频**：mall 主轮询失败时的 getV2 fallback 也要有独立预算，不能沿用 mall hot-path 频率。

## 4. ⚠️ 风控注意事项（最重要）

本接口前面挂着 B站的两级风控，**采集策略不当会被封**。以下均为实测结论。

### 4.1 两级风控状态机

```
   正常          突发/高并发            累计滥用
   200 ──────────▶ 429 ─────────────────▶ 412
    ▲  (OpenResty边缘            (Gaia安全层, IP封)
    │   软限流,概率丢弃)               │
    └──── 概率恢复 ◀── 429 ◀───────────┘  静默 ~8–9min 先降级回429
```

| | **429 软限流** | **412 硬风控** |
|---|---|---|
| 含义 | 「请求过于频繁」 | 「触发哔哩哔哩安全风控策略」+验证码 |
| 产生层 | OpenResty 边缘网关 | Gaia 安全层（响应头带 `x-sec-request-id`） |
| 触发 | 瞬时突发/节点负载 | **累计**请求量达 IP 信誉阈值 |
| 维度 | **纯 IP**（与 cookie/buvid 无关） | **纯 IP**（换 buvid 无效） |
| 持续 | 秒级，**可立即重试** | **~8–9 分钟**，静默也不提前解 |
| 处理 | 退避后重试，正常现象 | 只能换出口 IP 或等 TTL |

### 4.2 必须遵守的采集纪律

1. **`buvid` cookie 不能救你**。实测带不带 buvid3，429 概率完全一致；触发 412 后换全新 buvid3 仍是 412。**429/412 是 IP 维度，换 cookie 解决不了**（TLS 指纹是另一道独立闸门，只决定单次请求能否通过，见 `bilibili-endpoints-comparison.md` §4）。
2. **控制频率，串行为主**。建议**单出口 ≤ 1 req/s**，多项目轮询要**串行排队**而不是并发齐发。实测并发 10 齐发即 ~20% 被 429，25 齐发 ~32%。
3. **429 是正常现象，退避重试即可**，但**不要无脑高频重试**——429 的累计会升级成 412。建议指数退避（如 1s→2s→4s，上限 30s）。
4. **绝不要为了"更实时"而提高并发或频率**。一旦从 429 累积到 412，该出口 IP 会被封 ~8–9 分钟，期间所有项目监控全部中断，得不偿失。
5. **412 出现时的正确反应**：立即停止该出口的所有请求，静默等待（或切换出口 IP），**不要继续探测**（探测会刷新/延长封禁）。
6. **多 IP/代理池要克制**：把负载摊到多个出口能提总吞吐，但每个出口仍要守 §4.2.2 的低频纪律；否则只是让多个 IP 一起进 412。
7. **热门项目风控更严**（`hotProject:true`、开售前后时段）。开售瞬间是风控最敏感的时刻，监控频率反而要更保守。

### 4.3 推荐轮询参数（经验值）

| 场景 | 单项目轮询间隔 | 说明 |
|---|---|---|
| 普通项目、非临近开售 | 30–60 s | 商详本身有服务端缓存，更快无意义（§5.2）。 |
| 临近开售（前 5 min） | 10–20 s | 抓 `未开售→在售` 翻转。 |
| 售罄回流捡漏 | 20–30 s | 回流是随机弃单，秒级监控价值不大且风险高。 |
| 触发 429 后 | 退避 ≥ 2× | 指数退避，封顶 30 s。 |
| 触发 412 后 | 停 ≥ 10 min | 或切换出口 IP。 |

## 5. ⚠️ 数据可靠性陷阱

### 5.1 `num` 是「可购买数量」，跌破限购时就是精确余量 —— 这是核心余量信号
> 注意：「未开售」「已售罄」状态下 `num` 本就为 0，不能据此认为 `num` 不反映余量。对**在售**项目实测的模型如下。

**`num = min(真实库存 stock, 限购上限 static_limit.num)`**（真实库存 `stock` 前端不可见）。由此：

| 观测 | 含义 | 余量判断 |
|---|---|---|
| `num == static_limit.num`（顶格，常伴 `num_type=2`） | 库存 ≥ 限购，被限购盖住 | **充足**：只知 `≥ 限购数`，真实库存未知（可能成千上万） |
| `0 < num < static_limit.num`（常伴 `num_type=1`） | 库存已跌破限购数 | **`num` 即真实剩余张数**：越小越告急，是售罄前唯一精确余量 |
| `num == 0` | 无库存（或未开售） | 售罄 / 未开售（结合 `sale_flag` 区分） |

实测佐证（在售项目快照）：某话剧三个价位分别 `num=0`(已售罄)、`num=5`、`num=6`（`static_limit.num=8`）；某音乐会 D 档 `num=5`、其余档 `num=8`(顶格)。即同一项目内 `num` 会随各档库存独立下探。

**对监控的意义（重要）**：
- **判断"充足"** = `num >= static_limit.num`（顶格）。但**无法得到顶格以上的真实库存**，"充足"只意味"≥限购数"。
- **告急/精确余量** = `num < static_limit.num` 这一翻转，此刻 `num` 就是真实剩余张数 —— **最高价值的早期售罄预警信号**，应单独建告警（如 `num` 跌破阈值、或环比下降速率）。
- **回流捡漏** = 监控 `num` 由 `0`→`≥1`（弃单回流）。比只看 `sale_flag` 翻转更灵敏。
- 仍需注意是缓存数据、有秒级延迟（§5.2），`num` 是展示级近实时值，非交易级强一致。
- `static_limit.num` 因项目而异（实测有 `4`、`8` 等）；判定"顶格"必须用**该 SKU 自己的 `static_limit.num`**，不可硬编码常数。

### 5.2 商详是缓存数据，有秒级延迟
响应头 `cache-control: no-cache` + `x-cache-webcdn: BYPASS`，但官方明确商详走**服务端多级缓存**（本地 Caffeine + Redis）。因此 `sale_flag` 等状态相对真实库存**可能有秒级延迟**。监控到的"已售罄"可能比实际晚几秒，反之亦然。**不要把本接口当作交易级实时数据源**，它是"展示级"数据。

### 5.3 时间处理：用服务端时间，别用本地时钟
- 倒计时直接用 `count_down` / `bs_countDown`（秒），或用 `sale_start - current_time` 计算。
- `current_time` 是服务端时间戳，**始终以它为基准**对齐，避免采集机时钟漂移导致"开售提醒"早报/漏报。
- 时间戳单位是**秒**（不是毫秒）；`sale_start` 同时给了时间戳(`saleStart`)和字符串(`sale_start`="2026-06-21 12:00:00")两种格式，监控逻辑用时间戳，展示用字符串。

### 5.4 价格单位是「分」
`price`、`price_low/high` 均为分，展示需 `/100`。例：`price:138000` = ¥1380，`price_low:12800` = ¥128。

### 5.5 状态分散在三层，别只看顶层
项目可能 `sale_flag=在售`，但某个 `screen` 已售罄，或某个 `ticket` 已售罄。**告警必须下钻到 SKU 级**（`ticket_list[].sale_flag`），只看项目级 `sale_flag` 会漏掉"还有 D 级、但 S 级已抢光"这类情况。`sales_dates[].label="无票"` 也是整日售罄的快捷信号。

### 5.6 字段可能为 null / 缺失
未登录态下 `merchant`、`mid`、`venue_info.traffic` 等被脱敏为 `null`；`couponList`、`activity_list` 等营销字段常为 `null`。解析时全部做空值保护，不要假设字段一定存在。

### 5.7 结构可能随版本变化
`getV2` 是相对新版（`ticketDetailNewModel:true`），字段会随前端迭代增减。监控解析层应**只依赖明确用到的字段**并容忍未知字段，避免新增字段导致整条解析崩溃。

## 6. 一个最小可用的采集循环（伪代码）

```js
// 单出口、串行、低频、退避；状态以 sale_flag 为准
const projects = [1001701, 1001653 /* ... */];
let interval = 45_000;                       // 基础间隔

async function pollOnce(pid) {
  const r = await fetch(getV2(pid), { headers: UA_REFERER });
  if (r.status === 412) { backoffHard(); return; }      // 硬风控：停 ≥10min/换IP
  if (r.status === 429) { backoffSoft(); return; }       // 软限流：指数退避
  resetBackoff();
  const d = (await r.json()).data;
  for (const s of d.screen_list ?? [])
    for (const t of s.ticket_list ?? [])
      emitIfChanged({                                    // 只存变更
        pid, screen: s.id, sku: t.id, name: t.desc,
        flag: t.sale_flag?.number,                       // ← 售卖状态
        clickable: t.clickable,
        price: t.price / 100,
        num: t.num,                                      // 可购买数 = min(库存,限购)
        limit: t.static_limit?.num,                      // 限购上限(num 的封顶)
        ample: t.num >= (t.static_limit?.num ?? Infinity),// 顶格=充足(≥限购)
        remain: t.num < (t.static_limit?.num ?? Infinity) // 跌破限购→num即真实余量
                  ? t.num : null,                        //   告急信号：单独告警
        serverTs: d.current_time,                        // ← 用服务端时间
      });
}

// 所有项目串行排队，整轮节流到 ≤1 req/s
async function loop() {
  for (const pid of projects) { await pollOnce(pid); await sleep(1100); }
  setTimeout(loop, interval);
}
```

## 7. 一页速记（TL;DR）

- ✅ 用 mall 商详做主监控，用 `getV2` 做低频兜底/交叉校验；**状态看 `sale_flag`/`clickable`**，下钻到 SKU 级。
- ✅ 时间用 `current_time`/`count_down`（秒）；价格 `/100`。
- ✅ `num = min(库存,限购)`：顶格(`=static_limit.num`)=充足；跌破即真实余量(告急信号)；`0`=售罄。本接口是展示级缓存，有秒级延迟。
- ⚠️ 风控是 **IP 维度**：单出口 **≤1 req/s + 串行 + 退避**；buvid 救不了你。
- ⚠️ `429`=软限流可重试；`429` 累积会升级 `412`=IP 硬封 **~8–9 分钟**，出现就停手/换 IP。
- ⚠️ 别为"更实时"提并发——开售瞬间风控最严，反而要更保守。
